# HZERO 交付设计工作流

端到端地完成从原始资料到专业设计文档的交付。输出物为图文并茂、结构完整的 Word/PDF 文档。

## 工作流总览

```
原始资料（需求/会议纪要/数据/原型/访谈记录）
  │
  ▼
阶段1: 资料分析 ─── 提取关键需求、约束、风险、关键决策
  │
  ▼
阶段2: 架构设计 ─── 系统架构、模块划分、技术选型、依赖关系
  │
  ▼
阶段3: 详细设计 ─── 逐模块的接口、数据模型、流程设计
  │
  ▼
阶段4: 文档组装 ─── 调用 minimax-docx 生成专业排版文档
  │
  ▼
输出: 交付级设计文档（DOCX / PDF）
```

## 触发条件

当用户给出以下任何形式的原始项目资料，并要求生成本文档中描述的交付物时触发本技能：
- "帮我做一份HZERO交付方案/设计文档"
- "基于这些材料生成设计蓝图"
- "从需求到设计方案"
- 任何涉及"出设计文档"的完整交付场景

## 核心原则

1. **分阶段推进，不跳跃** — 每个阶段完成后再进入下一阶段
2. **多轮生成，不是一次写完** — 每个阶段内需要生成 → 审查 → 修正的循环
3. **子代理并行工作** — 大型文档的不同章节由子代理并行输出，避免长上下文衰减
4. **专业排版** — 最终文档使用 `minimax-docx` / `minimax-pdf` 技能渲染
5. **图文并茂** — 架构图、流程图使用 Mermaid → 渲染为图片 → 插入文档

## 阶段1：资料分析与需求梳理

### 输入
- 用户提供的原始资料（需求文档、会议纪要、数据、截图、原型等）
- 用户可能口头描述项目背景

### 输出
- 需求分析报告（markdown，暂存为工作文件）
- 关键功能列表
- 约束条件列表
- 风险点识别

### 执行步骤

1. **读取所有输入材料** — 打开所有用户提供的文件，理解全貌
2. **提取关键信息** — 识别：业务目标、功能需求、非功能需求、约束条件、假设、依赖关系
3. **结构化输出** — 在 `memory/design-cache/` 下生成 `01-requirements-analysis.md`
   - 格式：项目概述 → 需求列表（优先级分组） → 约束 → 风险 → 待确认项
4. **确认与用户对齐** — 将分析结果总结给用户，确认理解正确，补充遗漏
5. **标记所有待确认项为✅或⏳** — 得到用户确认后继续

## 阶段2：架构设计与方案规划

### 输入
- 阶段1输出的 `01-requirements-analysis.md`
- HZERO 平台能力参考（见 `references/` 目录）

### 输出
- 架构设计文档（`02-architecture-design.md`）
- 模块划分图（Mermaid → 渲染）

### 执行步骤

1. **系统架构设计**
   - 确定系统边界和外部依赖
   - 参考 `references/hzero-platform-architecture.md` 了解 HZERO 平台架构
   - 模块拆分：按 HZERO 微服务规范划分服务边界
   
2. **技术选型**
   - 后端：HZERO SpringCloud 生态组件
   - 前端：Choerodon UI Pro 组件库
   - 数据层：MySQL + Redis
   
3. **生成架构图** — 使用 Mermaid 语法绘制：
   ```markdown
   ```mermaid
   graph TD
     subgraph "服务层"
       A[服务A] --> B[服务B]
     end
     subgraph "数据层"
       C[(MySQL)]
     end
   ```
   ```
   - 将 Mermaid 渲染为 PNG（使用 `mmdc` 或 Puppeteer/Python）
   - 保存到 `assets/diagrams/` 目录

4. **输出结构化文档** — `memory/design-cache/02-architecture-design.md`
   - 系统架构 → 模块列表 → 模块职责 → 接口关系 → 技术栈 → 数据流
   - 包含渲染后的图片路径

## 阶段3：详细设计

### 输入
- `02-architecture-design.md` 中定义的模块列表

### 执行方式
每个主模块由**独立的子代理**负责详细设计，并行执行以提高效率：

对于每个模块，执行：
1. 数据模型设计（实体、字段、关系）→ ER 图
2. 接口设计（REST API 定义、请求/响应格式）
3. 业务流设计（状态机、时序图）→ Mermaid 渲染
4. 关键实现细节（特殊业务逻辑、约束校验）

### 输出
- 每个模块生成独立的 markdown 文件：
  `memory/design-cache/module-{模块名}.md`

### 注意事项
- 当模块数量较多时（>3），使用子代理并行生成
- 每个子代理需要接收：模块定义、架构上下文、HZERO 规范参考
- 各模块设计完成后，检查交叉依赖的一致性

## 阶段4：文档组装与排版

### 输入
- 阶段1-3 生成的所有设计文件
- `memory/design-cache/` 下的全部中间产物

### 输出
- 最终交付文档（DOCX 优先，可选项导出 PDF）

### 执行步骤

1. **合并所有设计内容** — 汇编为完整文档结构
2. **调用 `minimax-docx` 技能生成专业排版文档**
   - 使用 Pipeline A（CREATE）
   - 读取 `minimax-docx` 的 `Samples/AestheticRecipeSamples.cs` 选择适合的模板配方
   - 推荐：`ModernCorporate` 或 `ExecutiveBrief` 风格
3. **文档结构**：
   - 封面页（项目名称、日期、版本）
   - 目录页（自动生成 TOC）
   - 第1章 项目概述
   - 第2章 需求分析摘要
   - 第3章 系统架构设计（含架构图）
   - 第4章 模块详细设计（每模块为一节）
   - 第5章 数据模型（含 ER 图）
   - 第6章 接口设计
   - 附录（待确认项、术语表）
4. **图片插入** — 确保所有渲染的 Mermaid 图被正确插入
5. **运行验证管道** — 执行 `minimax-docx` 的 validation pipeline
6. **预览并确认** — 生成 `scripts/docx_preview.sh` 预览
7. **可选** — 用 `minimax-pdf` 技能导出 PDF 版本

## 关键工具链

| 目的 | 工具/技能 | 说明 |
|------|----------|------|
| 图表绘制 | Mermaid → 渲染为 PNG | 架构图、流程图、状态图、时序图 |
| Word 文档 | `minimax-docx` skill | 专业排版，封面、目录、页眉页脚 |
| PDF 导出 | `minimax-pdf` skill | 可选，用于客户交付 |
| 并行工作 | OpenClaw sub-agent | 多模块详细设计并行产出的编排 |
| 中间产物 | `memory/design-cache/` | 存放所有设计过程文件 |

### Mermaid 渲染方法

```bash
# 方法1: mermaid-cli (推荐)
mmdc -i diagram.mmd -o diagram.png -w 1200

# 方法2: 浏览器渲染
# 使用 headless 浏览器打开 https://mermaid.live/ 的渲染端点
```

## 输出质量检查清单

- [ ] 需求分析完整，无遗漏项
- [ ] 架构设计符合 HZERO 平台规范
- [ ] 每个模块的接口定义完整（CRUD + 业务接口）
- [ ] 数据模型设计的字段类型、长度、约束明确
- [ ] 文档结构完整（封面、目录、章节、附录）
- [ ] 图片（架构图/流程图）正确嵌入
- [ ] 表格样式统一，无格式污染
- [ ] 目录页自动生成页码（TOC 字段）
- [ ] 无未确认的待办项（所有 ⏳ 已处理）
- [ ] 文档可打印/导出，无分页异常

## 加速技巧（常见场景跳过）

- **如果用户已经提供了需求文档** → 跳过阶段1，直接从阶段2开始
- **如果只做一个小功能的方案** → 跳过阶段3的并行子代理，直接单线生成
- **如果用户指定不需要图表** → 跳过 Mermaid 渲染步骤
